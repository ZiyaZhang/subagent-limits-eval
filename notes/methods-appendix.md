# 附录草稿：方法、设计、判分（我写的部分）

2026-10-09 起草，主批还在跑。带【待填】的地方等结果出来再填，其余现在就是定稿口径。正文“我们怎么跑的”一节用第 0 段和表 A1，其他都留在附录。

## 0　给正文用的一段话

我们在 DSH 0.2.0-rc.2 上跑了 2,200 次任务，每次一个独立容器。主体是 DeepResearch Bench II 的 66 道中文调研题：同一道题在 20 多种设置下各跑一到两次，设置只差三样——能不能开 subagent、能开几层（深度上限 D）、同时最多几个活着（并发上限 K），外加几句写在题面里的指令。模型是 deepseek-flash；另用 deepseek-v4-pro 把其中四种设置重跑了 40 道题。报告由评测集官方的判分模型 GPT-5.5 逐条对照专家写的评分项打分，判分时看不到设置。方案、题目、设置、判分提示词和分析脚本都在开跑前或判分前提交到仓库，时间戳可查。

## A2　研究对象

DSH 的主 agent 可以调用工具开后台 subagent，subagent 自己也是一个完整的 agent。两个上限管这件事：

- 深度上限 D。0 表示不给开 subagent 的工具；1 表示主 agent 能开、subagent 不能再开；2、3 依次多一层。
- 并发上限 K。同一时刻还没结束的 subagent 数，超过就不能再开。

两个上限都是“超出即拒绝”。模型事先不知道上限是多少；开 subagent 的调用超限时返回一条错误，错误里带着上限的数字，之后怎么办由模型自己决定。出厂默认是 D=1、K=8。两条错误的原文：

- `Error: subagent depth 2 exceeds maxDepth 1`
- `Error: subagent limit reached (active child limit: 8); wait for an existing child to finish or complete this work with the current agents`

所有运行都打了一个补丁：进程等 subagent 都结束再退出。不打的话，命令行一次性运行里主 agent 一答完进程就退，深度 2 以上常在退出时崩溃。

## A3　任务与质量指标

调研题用 DeepResearch Bench II 的全部 66 道中文题。每道题附一篇来源文章和约 70 条专家写的评分项（最少 38 条，最多 176 条），评分项只有“满足”和“不满足”，分三类：信息召回、分析、呈现。质量 = 满足的评分项占全部评分项的百分比。题面写明不得使用来源文章，容器里屏蔽了它的网址。

编码题三道，都不联网：一道要补全 61 个文件的大型编码题（3,737 个隐藏测试）；24 道互相独立的练习；一道 16 步必须按顺序做的题。质量是隐藏测试的通过比例。

## A4　怎么跑

- 一道题的各种设置编成一个区组，同一轮一起提交、顺序随机。第一轮跑完全部题的第一次重复，再跑第二次重复。
- 每次运行一个容器，4 核 16 GB（大型编码题 64 GB：32 GB 下冒烟时内存被杀，交付虽完整但按规则不算正常结束，正式跑改成 64 GB），调研题限时 90 分钟（v4-pro 120 分钟）。主批和 v4-pro 批 32 路并发，编码题 12 路。
- 只有基础设施故障才重跑（容器开不出、文件拷不进拷不出、第一次回复前接口报错），每格最多 3 次。DSH 崩溃、超时、内存被杀都算结果。
- 费用 = 模型费加搜索费。模型费按三类 token 乘公开的高峰价；搜索工具每次调用背后还有一次模型请求，日志不记它的用量，我们从主批全部 45 万个搜索请求里随机抽 100 个原样重发，100 个都拿到用量，每次平均 0.0231 元（高峰价，最便宜 0.0057，最贵 0.0957；平均每次输入 7,897 token、其中缓存命中 2,217，输出 902）。每次运行的搜索费 = 它的搜索请求数乘这个单价。
- 时间 = 从开始到主 agent 给出最终回答，也就是用户等的时间。

## A5　分析

每个对比只拿它涉及的两种设置的运行，拟合一个分层模型：题是随机效应，设置是固定效应；一种设置每题有两次时再加一项题与设置的交互方差。旁边并列题内配对差的 t 区间，两者差得多就查原因。质量报差值，费用和时间取对数后报倍数，都带 95% 区间。

判断只用三个词。优效：区间下限大于 0。显著更差：区间上限小于 0。没测出：区间含 0，这时写明排除了多大的损失和多大的提高。不用“非劣”“等价”：开 subagent 的全部好处只有三四分，任何像样的容忍线都和效应一样大。

事前写定 9 个确认性对比，算一个家族，用 Holm 校正；要同时满足区间不含 0 和校正后 p 小于 0.05 才配“优效”或“显著更差”。其余对比都是探索性的，只给区间。

| 编号 | 对比 | 检验什么 |
|---|---|---|
| C1 | 默认对不开 | 开 subagent 是否优效 |
| C2 | K=4 对默认 | 把 K 减半是否显著更差 |
| C3 | 深度 2 配 K=8 对默认 | 放开一层是否优效 |
| C4 | 深度 3 配 K=8 对深度 2 配 K=8 | 再放开一层是否优效 |
| C5 | 深度 2 配 K=16 对深度 2 配 K=8 | 深度 2 下放开 K 是否优效 |
| C6 | 指令拆 8 份对指令拆 3 份（都配 K=8） | 多开是否优效 |
| C7 | 指令拆 8 份时 K=4 对 K=8 | 模型想开 8 个而上限只给 4 是否显著更差 |
| C8 | 指令拆 8 份时质量随 K（2、4、6、8）的线性趋势 | 趋势是否为正 |
| C9 | v4-pro 上默认对不开 | 换模型后是否仍优效 |

每个确认性对比另算五个版本，和主版本并排：把失败的运行也算进去（没交报告的记 0 分）；把被标为泄漏的运行也算进去；只用第一次重复；去掉撞上接口故障的区组；只用第一阶段没用过的 33 道题。

哪些运行不进主版本，事前写死：没有正常结束的（提前结束、退出时崩溃、超时、内存被杀）；没交出报告的；被标为泄漏的。泄漏的标记有三个来源：日志里出现评测集的名字；读入了题目禁用的来源；解盲前人工看过并判定照抄了来源的。默认或不开在某道题上的运行全被标记时，这道题退出该批全部对比。

## A6　判分与验证

- 主判是评测集官方的 GPT-5.5，提示词、每批 50 条评分项、三值记分都照官方脚本。开跑前拿第一阶段的 12 份报告各判两遍：官方默认的推理强度 medium 逐条一致率 0.959，没过事前定的 0.97；high 是 0.978，于是用 high。
- 跨厂商复判：Opus 判两成报告。【待填：kappa，有争议条目上的一致率】
- 自身一致：GPT-5.5 对一成报告再判一遍。【待填】
- 人工：同一道题同一条评分项在“不开”和“默认”两份报告上的两条判定算一对，抽 60 对共 120 条，其中 30 对是两个判分模型一致的、30 对是不一致的（方案原定 100 对，判分开始前按预案减到 60 对）。核对的人看不到设置、分数和模型的判定。【待填：人与 GPT-5.5 的 kappa；人工判定下默认对不开还剩多少】
- 长度：20 份报告各加三成无关但正确的文字再判，看分数变不变。【待填】
- 改坏：20 份报告各插入 3 条看着合理的错误事实再判。【待填】
- 泄漏：脚本查日志；解盲前人工看得分最高的 20 次运行；报告与来源文章的文字重合检查。【待填：各设置的泄漏率】
- 判分只读报告的前 15 万字符。【待填：超过的报告数和所在设置】

顺序是强制的：两张人工核对表填完、文件的 sha256 记下之后，才生成带分数的总表。

## A7　行为怎么量的

正文第 5.5 节的行为比例来自两套标注，都在判分阶段做，不加运行，也都不读分数和设置。

- **运行摘要。** 脚本先把一次运行的整棵 agent 树压成一份摘要：每个 agent 的任务原文、层、工具调用数、交回的头几百字、派出和被拒的调用；主 agent 的大事时间线、最终回答摘录、给出回答时是否还有 subagent 在跑；重复查询数；写完文件以后的复核波数。摘要里去掉组名和上限数字，保留题面末尾 150 字（判“开得过多”要知道题面要求拆几份）。主批 1,784 份摘要，中位数 7,388 字，上限 14,000 字。
- **运行级行为清单（照 MAST 的路：人定清单、模型标全量、人核一部分）。** 十项：主 agent 自己动手不派活、过早宣布完成、转包、重复分工、开得过多或开了不用、交回丢失、撞墙、循环、幻想协调、重复复核。判分模型（GPT-5.5，推理强度 medium）对每次运行逐项回答是/否/拿不准，每项要给一句摘要里的原话作证据。主批共 17,840 条回答，其中 17,802 条（99.8%）的证据句能在摘要里逐字找到。人工核对：每项抽模型判“是”和判“否”的各 3 条，只看证据句和它前后两三行，核对的人看不到模型的判断；“撞墙”全批只有 1 次运行判“是”，这一项是 1+3，全表 58 条。报每项的查准和漏判率，错超过三分之一的项只给例子不给比例。
- **subagent 再派活的分类。** 对每个派过活的 subagent，取它领到的任务原文和它派出去的每条任务，分成六类：原样转包、分片、收窄、新子题、复核、拿不准。先按文字重合率初筛，判断交给判分模型。主批 3,021 个这样的 subagent、7,745 条派出去的任务，证据句核对率 99.8%。人工核对每类 6 条共 30 条，同一次运行同一类至多 1 条。
- **给模型看的子任务文本。** subagent 派活时习惯先把自己领到的规则原样抄一遍，所以各条任务的开头往往一字不差。按固定长度截断会只剩这段共同开头：第一次试跑 40 个 subagent 的 102 条任务，有 20 条因此被判“拿不准”。改成开头 200 字照原样、其后凡与“它自己领到的任务”或“它派出的其他任务”逐字相同且连续 40 字以上的段落折叠成一句方括号说明（多少字、与谁相同），再取 1,000 字；类和定义没动，提示词加一条规则解释方括号。同样 40 个重跑：“拿不准”0 条，两次都给出明确类别的 82 条里 73 条相同，变的 9 条都在相邻的类之间。人工核对表用同样的显示。
- **两张核对表的答案键在填完之前不打开**，和判定核对、泄漏查看两张表一样：填完先记下答案文件的 sha256，再计分。

## A8　执行中出的事和处理

都在看到质量结果之前处理，逐条记在方案的变更记录里。

| 什么事 | 影响 | 处理 |
|---|---|---|
| 主批头三小时接口传输失败，模型请求反复自动重试 | 89 次运行有重试，其中 59 次等待超过自己回答时间的一成，集中在 3 个区组；同一道题的各种设置一起受影响 | 另出一版去掉这 3 个区组；主版本不动 |
| 跑到一半，运行结束后取回文件的步骤越来越慢，吞吐掉到每小时 15 次 | 不影响任何指标（时间取自日志）；18 次卡住的运行作废重跑 | 改成只取回小文件和会话日志，其余留清单 |
| 第一轮全部跑完才跑第二轮 | 默认的第二次比同题其他设置晚几小时到一天 | 另出一版只用第一次重复 |
| 深度 2 以上有运行在退出时崩溃 | 报告已交，但按事前规则不算“正常结束” | 主版本不含；“失败也算”版本包含 |
| 模块 O 是开跑后加的 | 不进确认性家族 | 标明探索 |
| 读日志的函数把 fork 出来的 agent 继承的父 agent 历史也算成它自己的 | 两阶段 5,129 次运行里有 3 次用过 fork，模型费被多算 22%–52%，主批合计多算 0.08%；第一阶段一次都没用过 | 改成只读继承标记之后的事件，受影响的表和普查重算；重建的主批运行表与原表只有这 3 行不同 |
| 判分模型每次都把某条评分项的原文改一个字（模糊表达→模糊表述），而脚本要求逐字相同才算回复有效 | 一道题的 24 份报告里有 6 份五次尝试全被判无效，分散在 6 个设置里各 1 份 | 改成“差一两个字且能唯一对上就算同一条”后补判，配对前后的原文逐条留档；模型、提示词、强度、分块和记分规则不变，已判好的 1,778 份没动 |
| Opus 复判比预计慢，和 GPT 第一遍并排提前跑时判不完 | 两路按同一份名单走会把剩下的报告各判两遍 | 链开始自己的 Opus 步骤时停掉提前那一路，剩下的由链判；抽样名单和并发不变 |
