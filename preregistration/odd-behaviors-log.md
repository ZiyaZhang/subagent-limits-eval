# 怪行为记录

她 2026-10-09 的要求：实验里或日常用 DSH 时出现奇怪的行为，要排查到原因并记下来。每条写清：看到了什么、多常见、成因查到哪一步（读到源码的给文件和行）、影响、建议。没查完的写明还差什么。

数据口径：主批 p2-main 的 1,784 次运行，脚本 scripts/tool_error_census.py 把全部“工具调用返回错误”按消息归类，共 50,751 次失败调用，其中打开网页 40,352 次、搜索 369 次（多为网站拒绝或超时），其余 10,030 次归成下面几类（数字是第 7 条的修正之后重算的）。源码行号取自 deepseek-harness 主干 a426d21d（2026-10-09）；实验用的是 0.2.0-rc.2，这几处的报错文字相同。

## 1　给已结束的 subagent 续发消息失败，转而另开一个接续的 subagent（她的截图）

- **看到的**：主 agent 想把新信息交回原来的两个 subagent，发送消息工具两次返回 `active teammate "<编号>" not found`，主 agent 判断“没有送达”，各开一个新的 subagent 接着查。原来两个 subagent 的上下文就丢了。
- **成因（已读到源码）**：两个插件注册了同名工具。
  - 普通的 subagent 控制工具 `send_message(agent_id, message)`：packages/subagent/tool-subagent-control/src/index.ts 第 28–72 行。说明写的是“空闲的 agent 收到消息会开始新一轮”，`list_agents` 的说明也写“直接子 agent 在任何状态下都接受 send_message”。
  - Agent Teams 插件在同一个 agent 的作用域里又注册了一套同名的 `send_message(target, message)`、`list_agents`、`interrupt_agent`：packages/experimental/tool-agent-team/src/index.ts 第 163 行起，`send_message` 在第 215–230 行。它按“队员名字”找收件人，而且只找还在队里的：packages/experimental/agent-team/src/roster.ts 第 42–54 行，找不到就抛这句 `active teammate "…" not found`。
  - 普通 subagent 结束时给父 agent 的通知是 `Background subagent <编号> finished and will do no further work unless you send it more.`（packages/subagent/subagent/src/continuation-messages.ts 第 106–112 行），等于提示模型“可以续发”。模型照做，拿 subagent 工具返回的编号去调 `send_message`，但此时这个名字指向的是 Agent Teams 那一个，编号不是队员名字，于是报错；报错里也没说该怎么办。
- **影响**：续不上原来的 subagent，只能另开，前面查到的上下文作废，多花一遍钱。
- **建议**：三选一或都做。同名工具不要两个插件各注册一套，Agent Teams 的那套改名或者兼容 subagent 编号；找不到收件人时报错里写明“这个编号是普通 subagent，不是队员”；Agent Teams 开着的时候，结束通知别再说“除非你再给它发消息”。
- **实验里有没有**：实验的配置没开 Agent Teams，这句报错一次也没出现。实验里对应的是第 2 条。
- **状态**：成因查清。还没做的：在她那个会话的日志里核对当时是不是开着 Agent Teams；要不要提 issue 由她定。

## 2　实验里 agent 之间的消息：11,539 条，失败 84 条

脚本 scripts/message_census.py 逐条看了主批里每一次 `send_message`：谁发给谁、对方当时还在不在干活、送没送到、没送到之后发的人做了什么。1,784 次运行里有 1,331 次用过，共 11,539 条，送达 11,455 条，失败 84 条（0.7%，分布在 46 次运行里）。

**送达的。** subagent 发给自己的父 agent 8,014 条，父 agent 发给自己的子 agent 3,441 条。其中发给“已经结束上一轮”的子 agent 229 条，224 条送达并把它重新叫起来，5 条被拒（见下表第三行）。所以在实验的配置下，结束了的 subagent 是能续上的；第 1 条里她看到的“续不上”来自 Agent Teams 那套同名工具，实验没开它。

**失败的 84 条。**

| 报错 | 次数 | 是什么情况 | 源码 |
|---|---|---|---|
| `subagent "<编号>" belongs to another parent session` | 32 | 31 条是越级：第 2 层的 subagent 直接发给主 agent 16 条，第 3 层发给第 1 层 15 条；1 条发给了自己。DSH 只允许发给直接的父 agent 或直接的子 agent | rc.2 的 dsh-subagent/lib/index.js 第 958 行 `authorizeLineage`；主干是 packages/subagent/subagent/src/manager.ts 第 715–725 行 |
| `subagent "<编号>" is unavailable` | 46 | 全部是模型把 36 位的编号抄错了。和本次运行里真实编号比，差 1 个字符的 29 条，差 2–3 个的 12 条，差得更多的 5 条；有相邻两位写反的、少一段的、少一个横杠的、混进一个不是十六进制的字母的。抄错的原本是自己父 agent 的编号 25 条、自己子 agent 的 16 条 | 同文件第 1911 行：按编号找不到会话，统一报这一句 |
| `subagent limit reached (active child limit: N)…` | 5 | 主 agent 给已结束的子 agent 续发消息，把它叫起来要占一个并发名额，当时名额满了（K=4 三条，K=6、K=2 各一条）。消息不排队，直接丢 | 同文件第 728 行 |
| `tool call aborted before dispatch` | 1 | 调用发出前这个 agent 被中止 | |

**失败之后做了什么。** 紧接着的下一步：再发一次 39 条（改对编号或改发给父 agent），先调 `list_agents` 查名单 15 条，这个 agent 之后再没有动作 10 条，其余 20 条转去做别的（跑命令、改文件、搜索）。六步之内另开一个新 subagent 来接替的只有 3 条，都在 K=4、要求拆 8 份的那一格：2 条是续发时名额满了，1 条是编号抄错。

**两处值得改的。**
- 编号太长，模型会抄错：每 250 条消息里有 1 条。报错只说“不可用”，没说这个编号根本不存在，也没列出能发给谁。建议：找不到编号时在报错里写明“没有这个 agent”，并列出发的人的父 agent 和子 agent 的编号；或者给 agent 起短名字。
- 越级汇报被拒时，报错说的是“这个 subagent 属于别的父会话”，而对方其实是发的人的祖父，读起来对不上。建议直接写“只能发给直接的父 agent 或子 agent，你的父 agent 是 <编号>”。

- **状态**：查清。各 K 下续发的次数：K=1 有 2 条、K=2 有 38 条、K=3 有 2 条、K=4 有 59 条、K=6 有 23 条、K=8 有 79 条、K=16 有 20 条、K=64 有 6 条。

## 3　改文件时报“文件在读过之后被改了”

- **看到的**：`edit` 报 `file changed since it was read — re-read the file, then retry` 782 次，出现在 416 次运行里；`write` 同类 45 次。另有 `old_string was not found` 538 次、`file has not been read` 274 次。
- **猜测的成因，未核实**：几个 agent 同时改同一份报告，或者 agent 自己用 bash 改了文件之后又用 edit。
- **还差的**：按“是谁在两次之间改了这个文件”分类，看是多个 agent 撞在一起还是自己撞自己；各 K、D 下的发生率。

## 4　工具调用被中止

- **看到的**：`bash` 返回 `tool call aborted` 364 次（263 次运行），其中 188 次之后这个 agent 再没有任何动作；另有 `aborted before dispatch` 59 次。
- **猜测的成因，未核实**：主 agent 给出最终回答时还在跑的 subagent 被中止。主批里见过一例：上限 K=2 时主 agent 想开 4 个，后 2 个等到名额才开出来，主 agent 写完报告就结束了，这 2 个被中止。
- **还差的**：被中止的 subagent 有多少、已经花了多少钱、它们的结果有没有被用上；和 K 的关系。

## 5　模型想拿评测集的题库

- **看到的**：搜索结果里出现了评测集题库文件的一个转载地址。5 次运行换着镜像和代理想把它下载下来（raw.githack、jsdelivr、ghproxy、Hugging Face 的接口，还有一次去查容器的 hosts 和本地代理端口），全部被容器的屏蔽挡住。另有 1 次运行下载了评测集的论文，从里面读到了自己那道题的要求原文。
- **处理**：这些运行都在泄漏标记之内，不进主版本。详见方案变更记录 2026-10-09T08:00Z 那条。
- **状态**：查清。

## 7　fork 出来的 agent，日志开头带着父 agent 的全部历史

- **看到的**：第 2 条的普查第一遍数出 66 条“兄弟之间互发并送达”的消息，而源码不允许这样发。追下去发现发的人都是用 `subagent_fork` 开出来的 agent，那 66 条是它们日志里父 agent 历史的副本，不是它们自己发的。
- **成因**：fork 出来的 agent 要继承父 agent 的上下文，DSH 把父 agent 到那一刻为止的全部事件原样抄进它的会话日志（调用编号、时间都和父日志相同，会话头里 `isSeeded` 为真），抄完写一个 `session/end-seed` 事件，后面才是它自己的。按“日志里有的都是这个 agent 做的”去读，父 agent 的 token、工具调用、搜索请求就在每个 fork 身上又被数一遍。
- **多常见**：扫了两个阶段全部 5,129 次运行，日志里带副本的 fork 只有主批 3 次运行里的 9 个，都是主 agent 在要求拆 8 份的格子里开的。主批里 `subagent_fork` 一共被调用 135 次（44 次运行），开成 78 个，其余 57 次被深度或并发上限拒绝；开成的 78 个里另外 69 个不带副本，原因见第 8 条。
- **影响**：这 3 次运行的模型费用原来被多算 22%–52%，主批合计多算 0.08%。第一阶段没有一次用过 fork，已发布的数不变。
- **处理**：读日志的函数改成对 fork 的日志只取 `session/end-seed` 之后的事件，受影响的表和普查全部重算，详见方案变更记录 2026-10-09T17:05Z 那条。
- **给 DSH 的建议**：这不是缺陷，但值得在会话日志格式的文档里写明；自己写脚本统计日志费用的人都会踩到。
- **状态**：查清，已改。

## 8　fork 出来的 agent 多数其实没有继承上下文

- **看到的**：主批开成的 78 个 fork 里，69 个的日志是从零开始的：没有父 agent 的历史，第一次请求的输入只有一千多 token（外加缓存的系统提示）。而模型给它们写的任务说明是按“对方看得到这段对话”写的，例如“核对本次对话里描述的那项任务的 A 部分”“只依据本会话中已经出现的原始文献”“与本次会话中已经核实过的来源一致”。按关键词粗数，69 条任务说明里至少 10 条明写了要依靠对话内容，这是下限。这些 fork 多数被用来做报告写完后的审查。
- **成因（已读到源码）**：fork 只复制父 agent “已经结束的轮次”，当前这一轮不复制；父 agent 一轮都没结束时，孩子从零开始。rc.2 的 dsh-subagent-fork-in-process/lib/index.js 第 23–28 行 `completedTurnPrefix`：取到最后一个 `turn/end` 为止，没有就返回空。无人值守的一次性运行里，主 agent 从收到题目到写完报告通常都在第一轮里，所以这时开 fork，连用户的原始题目都带不过去。那 9 个带副本的，是主 agent 结束过一轮（等 subagent 时停下、又被消息叫醒）之后才开的。
- **工具说明怎么写的**：`subagent_fork` 的说明是“孩子带着到目前为止所有已结束的轮次（看不到正在进行的这一轮）”，任务参数的说明是“它已经看得到这段对话已结束的轮次，放心在此基础上写，只说新的内容”（dsh-tool-subagent/lib/index.js 第 344–348 行）。字面上没错，但模型分不清自己是不是还在第一轮，照着“只说新的内容”去写，孩子就缺了背景。
- **影响**：审查型的 fork 拿不到它被要求对照的材料，只能对着报告文件本身挑毛病，或者自己重新去查。对实验结论的影响：主批 1,518 次带委派工具的运行里有 29 次开成过 fork，占 1.9%，不改变任何一格的结论，在正文“看到的行为”里提一句。
- **建议**：没有可复制的轮次时，让工具直接报错或在返回里写明“这个孩子没有继承任何上下文”；或者把正在进行的这一轮截到当前这次调用之前也带过去。
- **状态**：成因查清。还没做的：这 69 个 fork 交回来的内容有没有因为缺背景而跑偏（要读内容，量不大）。

## 不算怪、但数量最大的两类

`subagent` 被深度上限拒绝 4,397 次（739 次运行），被并发上限拒绝 3,096 次（687 次运行）。这是实验本身要量的东西，在正文里按设置报。
