## 题目候选

- 《Agent harness 里的 subagent 上限该设多少：并发与深度上限的测量》
- 《How many subagents, how deep? Measuring concurrency and depth limits in an agent harness》

## 一句话主张

业界给 subagent 的深度和并发默认值都是没有测量就定的；我们在一个开源 harness 上把两个上限逐档测了一遍，发现上限只在模型的需求超过它时才起作用，放开深度主要是多花钱，单 agent 自己多查追不上开 subagent、几份独立报告合并却追得上；据此给出测量得到的默认值和一套换模型重测的流程。

## 每节结果的写法

结果部分的单位是"发现卡"（10/8 她定）：一张卡一个发现、一页以内，内容照参照页的样子——一句话主张（她写）、一个表或一个数（只放会改变 harness 开发者做法的数）、一段真实运行片段（她从候选里挑）、一两条改进思路和谁该做。读完说不出"所以要改什么"的卡整张删；一个数只在一张卡上出现。候选卡：需求曲线、开不开的账、K 曲线、深度买到了什么、固定需求下的上限代价、收益从哪来、subagent 自己再派活（转包、分批、收窄、一上来就派）、被拒以后模型怎么办、主 agent 自己动手还是派活（模块 O）、换模型、harness 缺陷清单。

四段：做了什么、看到什么、一个例子、意味着什么。结论先列五到七条编号的发现，每条一句话一个数。算不出的量写明算不出，不估、不留空。一致率只说稳定性不说准确率。每个数只出现一次。效率指标并列：每元多写对几条、每百万 token 多少分。

四段是骨架，不是模板。每节的写法可以不一样：机制用箭头链（一个用户问题 → 几个 subagent → 每个几次搜索 → 每次搜索几个查询词），对比用一行一个条件，现象用一张截图加两句话。连续两节长得一样就改掉一节。

## 写作流程：谁写什么

组内读者不喜欢前几版，原因是太长、太齐、太像机器写的：每节同一个模板，每句都带限定，没有一处是人在说话。参照页「DSH web调用相关」只有七百字：数字先出，判断紧跟（"这个需要模型侧优化"），机制画成箭头链，没弄清的地方就写成问题（"需要确认一下这个 tool 的实验细节"），改进办法按收益排（"这个收益最高"），最后一个和竞品的对照用一句话评价（"工具调用比较克制，效果中规中矩，性价比不错"）。读者记得住，因为每一句都在传递一个判断。

照这个来，分工写死：

| 谁 | 写什么 | 什么时候 |
|---|---|---|
| 你手写 | 开头一段：什么事让你起了这个念头，用户怎么抱怨的，你当时猜什么 | 现在就能写 |
| 你手写 | 解盲后看着八张图说话，每张图一到两句，用你的话；我逐字记下来 | 第 3 天解盲当天 |
| 你手写 | 结论的五到七条编号发现，从上面那些话里挑 | 第 3 天 |
| 你手写 | 改进思路一节，按你认为的收益排 | 第 4 天 |
| 我写 | 方法、设计、判分、附录、表和图、图注 | 已有材料 |
| 我改 | 把你的句子放进结果节当每节的第一句和最后一句，中间填数和例子；不改你的用词 | 第 4 天 |
| 一位同事读 | 读十分钟，合上文件复述发现；复述不出来的段落删或重写 | 第 5 天 |

文字规则，和上面"写法约定"并用：
- 判断要有人说。"我们认为""最值得改的是"可以写，不躲在"结果表明"后面。
- 没弄清的写成问题，不写成"值得进一步研究"。
- 区间和小数留在表里；正文的数取整，一句一个。
- 每节至多一个"意外"、一个"问题"，没有就不硬凑。
- 不为完整而写：读者十分钟内不需要知道的进附录。

## 改进思路（讨论里的一小节，不改主线）

学参照页的做法，结果之后给一小节"对 DSH 的改进思路"，按预期收益排，每条一句话说证据、一句话说改法、一个数说收益。先按第一阶段的数预填，第二阶段出数后换成实测，顺序可能变。

1. 搜索那一路最值钱。调研类任务一半的钱是搜索费；参照页另查到搜索工具走的是带模型调用的 agent 模式，缓存命中只有 15%，每次约 1.1 万个未命中 token。改成不调模型的搜索接口，或者至少把每次搜索顺带生成的那段回答（占搜索请求费用 43%，插件并不用）去掉。预期：调研类任务费用降两到三成，和开不开 subagent 无关。
2. 退出前等 subagent 做完。命令行一次性运行时主 agent 一结束进程就退出，深度 2、3 下三分之一运行退出时崩溃；补丁后降到 5%。这是 bug，不是取舍。
3. 上限按任务类型给，不给一个全局数。调研类任务模型自己只开三四个，K=4 和 8 没有差别；编码任务每次都碰到 8。要么按任务类型配，要么把上限做成可见的，让模型知道还有几个名额。告知上限的 160 次说明只告知不改质量，但能省掉一半被拒的调用。
4. 写完以后的复核做成开关。大型编码题默认写完再派十个 subagent 复核，多等十八分钟、多花一倍多的钱，修掉最后一两个测试。让用户选要不要复核，比调 K 更直接。
5. 深度 2 换成"多做几份合并"。深度 2 费用近两倍、质量多两三分；四份单 agent 报告合并不比默认少、每条事实更便宜。如果第二阶段 G 模块复现，这是比放开深度更划算的做法，可以做成一个预设。
6. 给转手加护栏。subagent 还没做任何实质工作就把同一个任务再派出去，OpenCode 出过 20 层的链；DSH 靠深度上限兜底，但第一阶段默认格 90 次运行里 62 次有被深度上限拒绝的调用。可以在被拒消息里直接说"这件事你自己做"，或者在 harness 里识别"任务说明和自己收到的几乎一样"的委派并拒绝。收益看模块 I 量出来的转手率。
7. 选择性委派。GitHub Copilot CLI 只改编排策略，让主 agent 自己做窄活、只把宽的或可并行的活委派，工具失败少 23%、等待少 5%、质量没退。我们的办公题默认下模型已经比较克制，但编码题一次开二十个；按任务类型写一条策略，用模块 J 的对照测。
8. 便宜工作者。Cursor 用前沿模型做计划者、便宜模型做工作者，工作者费用从 9,373 美元降到 411 美元。DSH 的 subagent 工具已经支持给子 agent 配不同模型；模块 J 的 O5 就是这条在我们场景的检验。

每条改法都标明"证据来自哪个模块、第二阶段确认了没有"，没确认的写成待验证。

## 局限，照实列

- 不改题面时实际数量的因果效应识别不了；按触顶分组只是描述。
- 深度在一个上下文装不下的任务上的作用没有测。
- 一个 DSH 版本；两个模型；命令行一次性运行；任务都在一小时内。
- 质量是事实召回或评分项通过，不是用户偏好。
- 判分由模型做（评测集官方的 GPT-5.5，Opus 复判两成）；人工核对只有一人，按"对"分层抽样 200 条。
- 一次重复的格上两三分以内的差别排除不了；"没有差别"一律写成"没测出，排除了多大的差别"。
- 办公报告题只有第一阶段的数据，新判分模型重判后进附录，不进主结论。
- 代码题质量接近满分，只能比时间、费用、交付。
- 上限实现是"超出即拒绝、不预先告知"；排队或可见上限没测。
